## Phase 0: Research

### Unknowns Found

1. **Outlines `from_transformers` with Qwen3-VL multimodal inputs**: Does the Outlines wrapper correctly handle `Qwen3VLForConditionalGeneration` when images are passed via `inputs.Image()` alongside text?
2. **Outlines Generator JSON schema enforcement on VL models**: Does `Generator(..., output_type=ModelResponse)` constrain the *text* output to valid JSON while letting the vision encoder operate freely?
3. **Optimal `max_new_tokens` for CoT + JSON**: With reasoning chains, is 2048 sufficient for 100 samples without excessive OOM risk on typical consumer GPUs?

### Research Tasks

```text
Task 1 (Phase 0): "Research Outlines from_transformers compatibility with Qwen3-VL-2B-Instruct for multimodal structured JSON generation."
Task 2 (Phase 0): "Research Outlines Generator output_type behavior on vision-language models: verify vision encoder is not constrained by text logits processor."
Task 3 (Phase 0): "Research practical max_new_tokens for 2B parameter CoT reasoning on MMMU questions: verify 2048 is sufficient for 95%+ of samples."
```

### Findings Consolidated (research.md)

**Decision**: Use Outlines `from_transformers(model, processor)` + `Generator(outlines_model, output_type=ModelResponse)`.

**Rationale**: Outlines' `from_transformers` dispatches on model class. `Qwen3VLForConditionalGeneration` subclasses `GenerationMixin`, which Outlines supports. The wrapper builds a logits processor that constrains only the *decoder* text tokens; the vision encoder operates independently before the decoder begins. The `inputs.Chat()` + `inputs.Image()` pattern is the documented Outlines approach for VL models.

**Alternatives considered**:
- `lm-format-enforcer` — rejected because Outlines is already documented in the project and provides a cleaner `Generator` API with Pydantic-native integration.
- Unconstrained generation with post-hoc JSON parsing — rejected by constitution (Section 6).

**max_new_tokens**: 2048 is the default chosen by the user explicitly to support CoT. The 2B model with bfloat16 on a 6GB+ GPU can handle this. OOM risk exists on very long reasoning chains but is caught by the existing try/except in `evaluate_sample`.

**Adapter strategy**: If `from_transformers` requires minor tweaks for Qwen3-VL (e.g., explicit processor config), isolate those to `load_model_and_processor()`. The inference path (`run_inference`) uses `inputs.Chat()` and `generator(chat, max_new_tokens=...)` as documented.
